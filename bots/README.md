# Сбор данных: боты и импорт событий

**Статус компонента: «Реализовано частично».** Обработчики и связь с общей БД
запускаются локально. Проверка выполнялась на вымышленных событиях и с имитацией
Telegram API. К боевому каналу, боту и CRM проект при сдаче не подключён.

Основной [README](../README.md) описывает задачу, общие допущения, данные и запуск
дашборда. Здесь описаны только сбор и эксплуатация бота. ML обучается отдельно
и не меняет исходные события; его интерфейс описан в [ML README](../ml/README.md).

## Что сделано и чего не хватает

| Часть | Статус | Реализовано / требуется для завершения |
|---|---|---|
| Бот для пользователя | **Реализовано частично** | `/start`, источник, анкета, интерес к курсу, цена, лист ожидания, заявка менеджеру, мероприятия. Пройдены локальные сценарии; нужны токен и реальная проверка диалогов. |
| Наблюдение своих каналов | **Реализовано частично** | Различаются вступление, выход, блокировка и заявка на вступление; проверяется целевой канал инвайта. Нужны права администратора и проверка событий реального канала. Историю подписок до запуска восстановить нельзя. |
| Импорт заказов, оплат, возвратов | **Реализовано частично** | JSON → общая БД, атомарная загрузка, контроль сумм и повторов. Нет подключения к CRM/банку: отправитель JSON должен подтвердить оплату и связь покупателя с Telegram ID. |
| Восстановление после ошибок | **Реализовано частично** | Сохранённые входящие события, повтор обработки, очередь ответов, задержка при 429, локальная блокировка процесса. Проверено без сети; нужны мониторинг, резервные копии по расписанию и проверка аварий на сервере. |
| Передача рекламного токена с сайта | **Реализовано частично** | Есть `web/telegram-link.js`; на действующий сайт не установлен. |
| Пробное занятие и Telegram Payments | **Только спроектировано** | Полноценного сценария пробного занятия и обработчика `successful_payment` нет. Используется внешний JSON-импорт успешных платежей. |

Один код может одновременно обслуживать личный интерфейс и наблюдать несколько
собственных каналов. Это самостоятельный контур сбора: прогнозы не отправляются
пользователям автоматически и не считаются наблюдаемыми покупками.

## Проверить без токена и без сети

Из корня проекта, **Python 3.10+**, сторонних Python-пакетов для бота и БД нет.
Фактическая проверка выполнена на Python 3.12.14. `bot.py`, `collector.py`,
`runner.py`, `config.py`, `telegram_api.py`, `store.py` используют стандартную
библиотеку Python; `sqlite3` входит в неё.

```bash
python -m unittest discover -s tests -v
python -m bots.smoke
```

`bots.smoke` сам создаёт временную **синтетическую** базу, вызывает CLI и удаляет
её после завершения. Сетевых запросов и отправки сообщений нет. Проверены:
создание БД, импорт справочников, ссылка `/start`, повтор Telegram update,
ошибка несвязанного канала и её исправление, импорт частичных оплат и возврата,
повтор импорта, построение признаков, резервная копия и список ошибок.

Ожидаемый результат smoke: **1 пользователь, 1 заказ, 3 денежных события**
(4 000 ₽ + 6 000 ₽ − 3 000 ₽), **7 000 ₽** чистых поступлений и столько же
описательно атрибутированной выручки. Два события входа — запуск бота и вступление
в канал; это не два новых человека. Все цифры здесь — проверочный пример,
не продажи «Поступашек». Отказы с кодом 1 в журнале smoke ожидаемы для
несвязанного канала и запуска без токена; оба сценария проверяются явно.

Восемь отдельных тестов `tests/test_bots.py` проверяют границы инвайтов,
источники без платного размещения, повторы очереди, 429/403, ошибку импорта,
привязку набора данных, блокировку процесса и сброс устаревшего offset.

## Настройка реального запуска

Следующие команды задают рабочую процедуру; успешная работа с реальным
Telegram **не проверена**, поскольку токен и доступ к каналу не предоставлены.
Проверен безопасный отказ `run` без токена. `run` после настройки отправляет
ответы пользователям от имени бота, а `invite` создаёт ссылку в Telegram.

Скопируйте `.env.example` в `.env`, заполните поля и запускайте из корня проекта.

| Настройка | Значение |
|---|---|
| `DB_PATH` | Отдельный файл реальных событий, по умолчанию `data/postupashki.sqlite3` |
| `DATASET_ID` | Название набора, например `telegram_live`; одна БД — один набор |
| `BOT_TOKEN` | Токен вашего бота; не включать в репозиторий |
| `CHANNEL_IDS` | Числовые ID собственных каналов через запятую, отрицательные |
| `ADMIN_IDS` | Telegram ID организаторов, которым доступны `/attend` и `/complete` |
| `MANAGER_USERNAME` | Настоящий username менеджера без `@`; пустое поле отключает заявки |

Переменные окружения имеют приоритет над `.env`. `--db` имеет приоритет над
`DB_PATH`; `--env` выбирает другой файл настроек. Бот должен быть администратором
наблюдаемых каналов; создание инвайта требует соответствующего права.

```bash
python bot.py init
python bot.py import examples/catalog.template.json
python bot.py bind-channel main -1001234567890
python bot.py link campaign_token --bot YOUR_BOT_USERNAME
python bot.py run
```

Сначала замените примеры справочников реальными темами, курсами, каналами,
датами и токенами. **Не загружайте шаблоны как реальные данные.** Приведённый
ID канала — пример. `init`, `import`, `bind-channel`, `link` проверены в smoke
с его собственными значениями. Для новых БД происхождение данных по умолчанию
`unknown`, пока оператор отдельно не подтвердил его. Генераторы демо ставят
`synthetic`. Само имя файла или `DATASET_ID` не делает данные реальными.

Создание инвайта, после регистрации размещения и связи собственного канала:

```bash
python bot.py invite placement_1 main --name campaign_1
```

Ссылка сохраняется отдельно в `tracking_links`. Здесь пока нет режима
`--join-request`, повторного использования старой ссылки или отзыва созданной
ссылки при ошибке записи в БД. Эти сценарии старого прототипа в новую CLI
не перенесены. `invite` без реального API не проверен.

Это long polling. Существующий webhook программа не удаляет: при его наличии
запуск остановится с ошибкой. Одновременно должен работать один сборщик для
одного `bot_id`. Несколько ботов с разными ID могут писать в общую локальную БД
через короткие сериализованные транзакции. Масштабирование на несколько серверов
и промышленная нагрузка не проверены.

## Оплаты и эксплуатационные команды

Формат текущей БД — `{имя_таблицы: [строки]}`; старый формат
`dataset + records` не принимается. Справочники и известный `user_id` должны
существовать перед загрузкой заказа. Заказ передаётся вместе со всеми позициями;
деньги — целые копейки RUB. Остальные определения покупки, пакета и возврата
см. в общем README; [контракт](../docs/bot_contract.md) описывает поля событий.

```bash
python bot.py import examples/payment.template.json
python bot.py import inbox --watch 10
python bot.py errors
python bot.py retry-update 700 3
python bot.py retry-replies 700
python bot.py replay saved_updates.json --bot-id 700
python bot.py features
python bot.py backup backups/postupashki-copy.sqlite3
```

`payment.template.json` и ID в командах — шаблоны; подставьте существующего
покупателя, заказ, файл updates и ID бота. Полный независимый пример этих команд
исполняется через `python -m bots.smoke`. `--watch` — бесконечный режим до Ctrl+C;
его длительная эксплуатация не проверена. Сначала сформируйте JSON целиком,
затем перенесите его в `inbox` атомарным переименованием.

Повтор одинакового ID безопасен; изменение данных под тем же ID отклоняется.
Ошибочный файл откатывается целиком и попадает в `import_runs`. Подкоманды
`demo` и `forecast` относятся к демонстрации платформы и агрегатному прогнозу:
их инструкция находится в основном README. Обучение новых ML-моделей не
запускается при каждом Telegram update.

`replay` только обрабатывает сохранённые события и ставит ответы в очередь.
Отправка происходит при последующем `run`. Повтор обработки не создаёт
повторные бизнес-события. Для сетевых ответов абсолютная гарантия «ровно один
раз» отсутствует: если Telegram принял ответ, а процесс упал до сохранения
результата, ответ может быть отправлен повторно.

## Что наблюдается и что неизвестно

- **Что мы знаем:** поступивший `/start`, изменение статуса в своём канале,
  ответ анкеты, запрос цены, заявка, регистрация и предоставленная ссылка;
  импортированный платёж — только в пределах достоверности внешнего источника.
- **Что мы оцениваем:** связь продажи с маркетинговым касанием по правилам
  атрибуции. `/source` — ответ со слов человека, он участвует только в mixed.
  Прогноз вероятности покупки строит отдельный ML-контур.
- **Что пока узнать нельзя:** чтение постов и программы, реальная отправка
  сообщения менеджеру, полнота старой истории подписок и причинный эффект
  рекламы. Нет события ≠ человек не подписан. Требуются новые логи, подтверждение
  полноты сбора (`collection_periods`) и эксперимент, если нужен причинный эффект.

`/submit` сохраняет URL, но не открывает и не проверяет содержимое работы.
Завершение участия подтверждает организатор. Платёж сопоставляется по
подтверждённому Telegram ID, а не по имени или username. Автоматического
сопоставления старых продаж с подписчиками нет.

## Ограничения и публичная поставка

В первоначальном задании предполагался готовый open-source донор наблюдателя.
В предоставленном коде донор не выбран и лицензия стороннего проекта не
используется: это собственная реализация на стандартной библиотеке Python.
Поэтому требование «переиспользован готовый донор» **не выполнено**; его нельзя
заявлять в презентации. Упоминание aiogram в исходном промпте не означает,
что aiogram используется в программе.

Журнал `bot_updates.payload_json` сохраняет оригинальные Telegram updates;
они могут содержать имя, username и текст сообщения. `/privacy` сообщает о
сборе, но автоматические удаление/экспорт по запросу пользователя, срок хранения
и разграничение доступа к БД ещё не реализованы. Рабочие SQLite, резервные копии,
входящие JSON и `.env` не должны попасть в публичную сборку или скриншоты.
Публичные примеры и smoke содержат только вымышленные ID. Дашборд использует
обезличенные ссылки на записи; доступ к внутренней БД даёт больше информации.
