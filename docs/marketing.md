# Каналы и акции: дополнение v2

Реализованы отдельные связанные таблицы внутри одного SQLite-файла. Это позволяет
соединять источники, пользователей, предложения, акции и покупки по ID. Отдельные
файлы БД не нужны. Исходные 20 пользовательских признаков остаются в `user_features`;
новые признаки и показатели находятся в `channel_stats` и `promotion_stats`.

Рабочая база пустая. Модели не обучались, реальные боты и оплаты пока не подключены.

## Что добавлено в исходные данные

| Таблица | Что сохраняем | Как получаем |
|---|---|---|
| `channel_snapshots` | Число подписчиков, типичный охват поста за 24 часа, основной этап образования аудитории, дата замера, источник сведений | Владелец канала / маркетолог; состав аудитории — только сообщённая оценка |
| `placement_metrics` | Накопленный счётчик просмотров конкретного размещения и время замера | Владелец канала / маркетолог |
| `tracking_links` | Уникальная метка, источник, размещение, тип входа, наш канал назначения | Создаём при подготовке размещения |
| `promotions` | ID, название, тип акции, дата создания карточки | Служебный бот маркетолога |
| `promotion_versions` | Начало и конец, тип и размер скидки, промокод, сегмент, текст условий, отмена; время действия и регистрации версии | Служебный бот маркетолога |
| `promotion_courses` | Продукты, к которым относится конкретная версия акции | Вместе с версией акции |
| `promotion_offers` | Связь отправленного предложения с версией акции и причина выбора получателя | Бот отправки предложений |
| `promotion_responses` | Нажатие на предложение или явный отказ | Callback кнопки нашего бота |
| `order_promotions` | Основная акция заказа, предложение при наличии, основание связи | При оформлении заказа, по промокоду или подтверждению |
| `placement_promotions` | Какую акцию рекламировало размещение | Карточка размещения |

Справочники `channels`, `placements`, история `acquisition_events`,
`membership_events` и `placement_cost_events` уже были в v1 и используются дальше.
`placements.campaign_id` — свободная метка рекламной кампании из v1; это не внешний
ключ акции. Для связи с акцией используйте `placement_promotions`.

Типы акций: `discount` (скидка), `bundle` (пакет), `bonus` (бонус),
`warmup` (прогрев), `launch` (запуск). Тип скидки: `none`, `percent`, `fixed`.
`discount_value` — целое число процентов для `percent`, копейки для `fixed`,
ноль для `none`. Индивидуальные фактические цены остаются в `offers`, суммы
заказов — в `orders`/`order_items`: условия кампании их не заменяют.

`target_education_stage` и `target_job_search_status` описывают правило выбора
аудитории. `NULL` означает отсутствие ограничения. Для более сложного правила
есть `terms`; автоматического назначения предложений по этим полям пока нет.

`promotion_courses` — полный список продуктов версии. Версию и список передаём
одним пакетом. Изменение списка или условий требует новой версии. Нельзя задним
числом дописать продукт в уже существующую версию и тем самым изменить прошлые признаки.

Заказ может иметь только одну основную акцию. В этой версии совместные акции
на разных позициях пакета не раскладываются: вся сумма относится к основной акции.
Сохраняйте такое правило явно. Если потребуется сочетание нескольких акций,
нужно расширить модель распределением денег по позициям, а не дублировать заказ.

## Полезные входные признаки для будущих моделей

Это кандидаты: полезность проверим на реальных временных разбиениях, после сбора
данных. Статистические показатели канала используем только по состоянию на дату
прогноза, с размером и полнотой наблюдаемой выборки. ID остаются ключами связи.

| Уровень | Поле | Почему может быть полезно |
|---|---|---|
| Канал | `topic_id` | Соответствие рекламируемому курсу |
| Канал | `audience_stage` | Школьная, студенческая, профессиональная или смешанная аудитория |
| Канал | `subscribers` | Масштаб канала; это внешний замер, не число привлечённых |
| Канал | `typical_post_views_24h` | Ориентир доступного охвата |
| Канал | `snapshot_age_days` | Насколько устарел замер |
| Канал | `placements_count` | Сколько раз уже размещались в канале |
| Канал | `days_since_last_placement` | Давность последней закупки |
| Канал | `conversion_horizon` | Историческая конверсия за одинаковый срок |
| Канал | `cash_per_user_horizon_minor` | Исторические чистые поступления на привлечённого |
| Канал | `retention_horizon` | Доля оставшихся в нашем канале на горизонте |
| Акция | `kind` | Скидка, бонус, пакет, прогрев или запуск |
| Акция | `is_active` | Идёт ли акция на дату расчёта |
| Акция | `duration_days` | Общая длительность известного плана |
| Акция | `days_to_end` | Время до дедлайна; после конца отрицательное |
| Акция | `discount_type`, `discount_value` | Тип и размер скидки; интерпретируются совместно |
| Акция | `courses_count` | Число продуктов в предложении |
| Акция | `mean_discount_sent_pct` | Средняя реально предложенная скидка среди успешных отправок |
| Акция | `repeat_sent_users` | Наблюдаемая повторная отправка акции одним и тем же людям |

Для прогноза **до нового размещения** его будущий фактический охват, привлечённые
люди и покупки запрещены во входных данных. Доступны прошлые размещения и сведения,
известные до закупки. Для новой акции итоговые клики и продажи ещё неизвестны;
можно использовать условия и прошлую историю аналогичных предложений.

`placements_count`, суммы, отправки и отписки считаются за доступную историю до
`as_of`. Горизонтные показатели (`*_horizon`) относятся к первым N дням каждого
пользователя. `horizon_days` по умолчанию равен 30, можно задать 7 или 90.
`mature_users` и `commerce_observed_users` нужны для оценки надёжности конверсии,
а не для доказательства готовности модели при произвольном количестве строк.

## Статистика каналов

Каждая строка `channel_stats` — источник × дата × горизонт × выбранный наш канал.
При единственном `own_main` он выбирается автоматически. При нескольких нужно
указать `--main-channel`: выход из учебного чата не считается выходом из основного.

| Поле | Точное значение |
|---|---|
| `touch_users` | Уникальные пользователи с любым наблюдаемым входом из этого источника |
| `first_source_users` | Пользователи, у которых это первый наблюдаемый источник; каждый входит в одну такую группу |
| `returning_touch_users` | Пользователи с касанием из канала, перед которым уже было другое наблюдаемое касание, в том числе из этого же канала |
| `mature_users` | Из first_source_users: с первого входа прошло не меньше N дней |
| `commerce_observed_users` | Из mature_users: покупки наблюдались полностью от первого появления до конца их N-дневного окна |
| `buyers_horizon` | Уникальные покупатели среди commerce_observed_users; только новые после входа заказы с полной оплатой внутри окна |
| `conversion_horizon` | buyers_horizon / mature_users; NULL, если есть пробелы в требуемом сборе или нет зрелой группы |
| `net_cash_horizon_minor` | Платежи минус возвраты внутри индивидуального N-дневного окна по заказам, созданным после прихода; включая авансы |
| `cash_per_user_horizon_minor` | Предыдущее значение / mature_users, включая некупивших |
| `member_observed_users` | Люди из группы источника, у которых наблюдалось членство в выбранном нашем канале |
| `left_users` | Уникальные люди с подтверждённым переходом joined → left после прихода; повторный выход не удваивает человека |
| `banned_users` | Уникальные люди с переходом joined → banned; отдельно от добровольных выходов |
| `rejoined_users` | Уникальные люди с наблюдаемым новым вступлением после выхода/блокировки |
| `current_members` | Подтверждённо состоят в нашем канале на дату расчёта |
| `current_membership_unknown_users` | Текущее членство неизвестно: нет исходного состояния или был пробел наблюдения |
| `retention_eligible_users` | Зрелые пользователи с наблюдаемым членством до горизонта и полной историей после его подтверждения до горизонта |
| `retention_horizon` | Состоящие в нашем канале на горизонте / retention_eligible_users |
| `net_cash_to_date_minor` | Чистые поступления после входа от всей группы первого источника до as_of, по заказам, созданным после входа |
| `contribution_to_date_minor` | Предыдущая сумма минус комиссии и переменные затраты завершённых заказов; NULL при неизвестных затратах/комиссиях или незавершённом авансе |
| `ad_cost_minor` | Фактические расходы минус возвраты по опубликованным размещениям канала; нужна полная история ad_costs |
| `cost_per_first_source_user_minor` | ad_cost_minor / first_source_users, если у каждого пользователя группы есть известное размещение этого канала |
| `attributed_romi` | (contribution_to_date_minor − ad_cost_minor) / ad_cost_minor; требует известных сумм, положительных затрат и привязки группы к размещениям |

`returning_touch_users` может пересекаться с `first_source_users`: новый человек
мог прийти из канала и позже повторно перейти из него. Эти столбцы нельзя складывать.
`left_users` также может пересекаться с `current_members`: человек вышел и вернулся.
Блокировка считается отдельно. Проверка текущего состояния (`status_check`)
не выдаётся за событие выхода или повторного вступления.

Под «вышедшими из источника X» здесь понимаем **пришедших из X и затем вышедших из
нашего канала**. Личную историю вступлений и выходов внутри чужого канала база не
предполагает. Ссылка может быть переслана: она показывает маршрут, а не доказанное
членство в источнике. Число подписчиков внешнего канала хранится отдельными снимками;
разность таких снимков — изменение размера канала, не число конкретных отписок.

Строка `__unknown__` объединяет пользователей без первого внешнего источника,
включая органические/свои источники. Известная последующая реклама не переписывает
неизвестный первый источник. Сведения о собственном первом источнике сохраняются
в acquisition_events и исходном пользовательском признаке. Пользователь без
событий входа отсчитывается от first_seen_at, с явным неизвестным источником.

База не трактует отсутствие события членства как отписку. Числа наблюдаемых
событий могут быть нижней оценкой при неполном сборе; `quality_json` это обозначает.
Зрелость окна не заменяет полноту наблюдения. Молодые пользователи не попадают
в знаменатель 30-дневной конверсии.

Просмотры размещений сохраняются с датами, а не суммируются по нескольким замерам
одного поста. `placement_metrics` содержит накопленные просмотры, не уникальных
пользователей и не персональные прочтения. При сравнении охватов выбирайте замеры
через одинаковое время после публикации. Счётчик подписчиков не равен охвату.

## Статистика акций

`promotion_stats` — акция × дата × горизонт. Плановые поля берутся из последней
известной действующей версии. Все отправки и продажи объединяются по ID акции,
включая её прошлые версии.

| Поле | Точное значение |
|---|---|
| `sent_offers`, `sent_users` | Успешные отправки и уникальные получатели; не прочтения |
| `failed_offers` | Неудачные отправки, отдельно от успешных |
| `clicked_users`, `click_rate` | Уникальные получатели, нажавшие кнопку; доля от sent_users |
| `repeat_sent_users` | Получатели с двумя и более успешными отправками этой акции |
| `mature_sent_users` | Получатели, у которых прошли N дней с первой успешной отправки |
| `commerce_observed_users` | Из зрелых получателей: с полным наблюдением покупок до конца окна |
| `buyers_horizon`, `conversion_horizon` | Покупатели / зрелые получатели в N дней после первой отправки; учитываются только явно связанные с акцией заказы, созданные после отправки |
| `linked_paid_orders`, `linked_buyers` | Все связанные полностью оплаченные заказы и уникальные покупатели до as_of |
| `net_cash_minor` | Все наблюдаемые платежи минус возвраты связанных заказов, включая авансы; не только 30-дневное окно |
| `mean_discount_sent_pct` | Среднее 100 × (1 − offered_price / regular_price) по успешным отправкам |

Если акцию покупают по публичному промокоду без персональной отправки, покупка
войдёт в linked_paid_orders и деньги, но не в конверсию персональных получателей.
Два клика одного пользователя — один clicked_users. Оплата после окончания акции
допустима для заказа, оформленного в срок, но для conversion_horizon должна успеть
в соответствующее окно. Возврат не удаляет исторический факт полной оплаты.

`assignment_reason` сохраняет broadcast/segment/randomized/manual/model.
Для randomized обязательны experiment_id и experiment_group из offers.
Это запись факта распределения, а не реализация рандомизации или анализа эксперимента.
Неполучившие предложение контрольные пользователи потребуют отдельного журнала
назначений на этапе реализации экспериментов; отсутствие отправки не означает контроль.

**Связанные продажи и attributed_romi — описательная атрибуция, не прирост от акции
или рекламы.** Часть людей могла купить без воздействия. Для оценки дополнительного
эффекта позже потребуется отдельный эксперимент и модель. Текущая v2 не делает
выводов о причинном эффекте и не назначает рекомендуемые рекламные бюджеты.

## Деньги и полнота

Все суммы в копейках RUB. Доли хранятся от 0 до 1, ROMI = 0.25 означает 25%;
`mean_discount_sent_pct` уже выражен в процентах. Расходы на продукт в
`order_items.variable_cost_minor` — итог по позиции с учётом количества, не цена
одной единицы. Комиссия каждого платежа/возврата — отдельный фактический расход.
Ноль у комиссии означает подтверждённое отсутствие, NULL — неизвестно.

Маржинальный расчёт — упрощённый кассовый показатель: затраты завершённого заказа
полностью вычитаются и не восстанавливаются автоматически при возврате клиенту.
Фактическое восстановление себестоимости потребует дополнительного учёта. Это
не бухгалтерская прибыль. Предоплата по незавершённому заказу делает contribution
и ROMI неизвестными. Итоговый ROMI использует всю доступную историю; каналы с
разным возрастом рекламных закупок по нему напрямую не ранжируем. Для одинакового
горизонта уже доступны conversion_horizon и cash_per_user_horizon_minor.

`collection_periods` расширен доменом `ad_costs`. Подтверждайте его от заведения
плановых размещений до даты расчёта, включая предоплаты и возвраты. Без него
ad_cost_minor и ROMI будут NULL. `quoted_cost_minor` не подменяет реальные расходы.
При полном ad_costs и отсутствии платежей фактические расходы равны нулю.

Новые связи подтверждаются независимо: `promotion_offers` — полнота привязок
предложений к акциям, `promotion_responses` — реакций на предложения,
`order_promotions` — связи заказов с акциями. Старые домены offers и commerce
сохраняют прежний смысл. Без новых подтверждений наблюдаемые счётчики сохраняются,
но соответствующие доли становятся NULL. Старые подтверждения v1 не создают
ложную полноту новых маркетинговых данных.

## Запуск и переход с v1

Скопируйте файл своей базы для резервной копии. Из директории с README:

```bash
python -m postupashki_data --db data/postupashki.sqlite3 init
python -m postupashki_data --db data/postupashki.sqlite3 build-marketing --as-of 2026-09-12 --horizon-days 30
python -m postupashki_data --db data/postupashki.sqlite3 export-marketing --table channel_stats --as-of 2026-09-12 --out data/channels.csv
python -m postupashki_data --db data/postupashki.sqlite3 export-marketing --table promotion_stats --as-of 2026-09-12 --out data/promotions.csv
```

При нескольких своих основных каналах добавьте `--main-channel ИДЕНТИФИКАТОР`
к build-marketing и при необходимости export-marketing. Без фильтра экспорт
содержит все рассчитанные основные каналы; их когорты нельзя складывать.

`init` автоматически и транзакционно переводит схему v1 → v2, сохраняя исходные
строки и пользовательские снимки. Повторный init ничего не стирает. `schema.sql`
содержит исходную v1, `marketing_schema.sql` — миграцию, код initialize применяет
их в правильном порядке. Не запускайте SQL-миграцию повторно вручную.

Все события используют occurred_at < as_of и recorded_at <= as_of. Замеры
используют observed_at < as_of; планы — effective_at <= as_of и recorded_at <= as_of.
Ровно в момент окончания индивидуального окна денежное событие уже не входит
в это окно. Поздно зарегистрированный старый возврат не меняет ранее известную
историю. Повтор build-marketing пересчитывает только выбранный снимок.

Python API: `build_marketing(db, as_of, horizon_days=30, main_channel_id=None)`;
`export_marketing(db, 'channel_stats', as_of, path)` и аналогично promotion_stats.
Исходные события принимаются прежним `ingest(db, payload)`. Новые таблицы включены
в пустой `ingest_template.json`. Полные исполняемые вымышленные примеры находятся
только в `tests/test_marketing.py`.

Проверены арифметика, интервалы, повторные события, выход/возвращение/блокировка,
неизвестный источник, незрелая когорта, пропуски, поздние события, будущие условия,
возвраты, связывание заказа, миграция и CSV. Нагрузочное испытание не проводилось.
