# Дашборд: определения, интеграция и границы

Статус продукта: **«Реализовано частично»**. Локальная HTTP-цепочка с общей
SQLite-базой и синтетическими моделями проверена. Боевая загрузка данных
Поступашек и качество ML на них не проверены.

Расчётный код, валидация импорта, защита границы HTTP и разделение фактов/оценок
в автоматических проверках: **«Реализовано и проверено»**. Автоматическая
проверка UI использует Node VM с DOM-заглушками; это не проверка браузером.

## Запуск и проверка

Из корня проекта:

```bash
python app.py --db data/demo.sqlite3 --models ml/models --port 8501
python app.py --db data/demo.sqlite3 --export dashboard_demo.html
python -m unittest discover -s tests -v
python tests/check_http.py
node tests/check_ui.cjs
python tests/check_ml_http.py
```

Откройте http://127.0.0.1:8501. Первые семь вкладок используют только стандартную
библиотеку Python: обзор, размещения, рост каналов, события, воронка, временной
прогноз, когорты. Восьмая вкладка **ML-сценарии** отделена в навигации.
Для прогноза нужны зависимости и подготовленные модели из `ml/README.md`.
Без них основные вкладки работают, а ML показывает причину недоступности.
Обучение запускается отдельной CLI-командой; HTTP-маршрута обучения нет.

`check_http.py` создаёт отдельную синтетическую базу с платформенными фикстурами,
проверяет импорт, повтор, CSRF и откат ошибочного платежа.
`check_ml_http.py` копирует общую демобазу, вызывает оба прогноза и проверяет,
что операционные суммы не изменились. Последняя команда требует ML-зависимости.

## Общая база, разные вопросы

Параметр `--db` задаёт один файл для операционных вкладок и `ml_bridge.py`.
Параметр `--models` задаёт каталог сохранённых моделей, но не вторую БД.
У модели и БД проверяется совпадение метки происхождения. Синтетическая
модель не применяется к базе, помеченной реальными данными.

- **Что мы знаем**: зарегистрированные события, платежи, возвраты и расходы.
- **Что мы оцениваем**: атрибуция clean/mixed, вероятность покупки и условная
  допустимая цена рекламы.
- **Что пока узнать нельзя**: причинный прирост продаж без контроля воздействия;
  полные пересечения подписчиков внешних каналов без доступной идентификации.

API: `GET /api/ml/status`, `POST /api/ml/customers`, `POST /api/ml/channels`.
POST требует тот же CSRF-токен, что импорт. Результат клиентского прогноза
агрегирован; пользовательские строки не возвращаются. Сценарий не записывается
в платежи, события или фактические расходы. Фильтры операционного периода скрыты
в ML-разделе: у прогноза собственная дата среза и горизонт.

В UI задаются курс, дата, скидка, её срок, число плановых сообщений. Для канала
добавлены просмотры, целевой ROI, цена владельца и предположительная доля
дополнительных покупок. Без последней экономический потолок с причинной
интерпретацией остаётся пустым; отдельно показан сценарий 100% прироста.
Все комиссии, возвраты и расходы кампании в UI-сценарии равны нулю и явно
подписаны; расширенные экономические условия доступны через CLI.

Автономный HTML содержит снимок фактов и статуса ML. Расчёты новых сценариев
доступны в приложении, а не в экспортированном HTML.

## Идентификаторы и публикация

Локальная БД сохраняет первичные ключи. В `/api/report`, CSV интерфейса и
HTML-экспорте пользовательские ID, ключи заказа/платежа/события заменены
псевдонимами HMAC с отдельным секретом сеанса. Пригласительные токены и поля
контактов удалены из ответа. Тексты ошибок и имена импортированных файлов
не выгружаются; детали доступны в локальном журнале. Псевдонимизация не
превращает исходную БД в безопасную для публикации: реальные БД не сдавать.


## Общие правила

- Период интерфейса включает обе выбранные даты по UTC. SQL использует полуоткрытый
  интервал `[начало дня, начало следующего дня после конечной даты)`.
- Read-only запрос выполняется в одном снимке SQLite. Новые данные становятся
  видны при следующем обновлении. Ключи и исходные платежи не копируются.
- Факт выручки = записанные оплаты − записанные возвраты. Число заказов и покупателей
  считается уникально по положительным оплатам; возврат не является новой покупкой.
- Связь покупателя со своими событиями — проверенный положительный Telegram ID.
- Окно атрибуции отсчитывается **назад от оформления заказа**. Платежи частями и
  возвраты используют основания этого заказа. Касания после заказа исключены.
- First/last/linear применяются к подходящим касаниям. Linear распределяет долю
  по событиям; несколько событий одного источника получают суммарную долю.
- Clean: наблюдаемые `bot_start`, именная invite-ссылка, проверенный `tracked_click`
  с установленным источником. Отписки, заявки на вступление и служебные события
  не участвуют. `/start` без источника не превращается в manual_source.
- Mixed: clean + явный ответ человека. Календарный fallback допускается, если нет
  подходящего идентифицированного касания, и найдено **одно** совпадение: один
  товар, количество 1, известная обычная цена, действующая известная версия скидки,
  точная цена заказа и единственное связанное размещение. Совпадения нескольких
  акций/размещений, неоднозначные пакеты и сегменты не атрибутируются.
- Дата заказа принята точкой применения цены. Fallback не восстанавливает клики,
  личность или факт контакта с рекламой. Основание видно в карточке сделки.
- `Δ = mixed − clean` — дополнительно приписанная **знаковая** выручка. В периоде
  возвратов она может быть отрицательной. Ни один режим не является оценкой причины.
- Плашка качества: взаимно исключающие доли **положительных платёжных записей**
  clean / только mixed / без источника; доля опубликованных в периоде размещений
  с известной стоимостью; покрытие потоков; зарегистрированные ошибки.
- Полнота определяется подтверждёнными `collection_periods`, а не отсутствием
  ошибок. Без полного сбора показаны наблюдаемые суммы/счётчики, а показатели,
  требующие полной истории, могут быть `NULL`.

## Экономика и стоимость

`ROMI_attr = (приписанная выручка − зарегистрированные маркетинговые затраты) /
затраты`. В общем обзоре реклама относится к дате расхода/возврата, дополнительные
затраты — к дате события. Для общего ROMI дополнительно требуется подтверждённый
сбор рекламных затрат за период. Состав расходов не является бухгалтерской прибылью.

Стоимость скидки выводится только для заказа с явной связью `order_promotions`
и известными обычными ценами. Она распределяется пропорционально оплатам/возвратам
и не учитывается как второе уменьшение денежной выручки. В ROMI эта уступка **не добавляется повторно**: выручка уже получена по
сниженной цене. Это исправление первоначальной формулы исключает двойной
учёт скидки и согласует дашборд с ML-экономикой.

В размещениях: фактически записанная реклама (или явно отмеченная котировка),
прямые дополнительные денежные затраты; приписанная доля скидки — справочно. Если фактические расходы
записаны, но покрытие неполно, статус — «Частично записано». Выручка относится
к выбранному периоду, затраты размещения — ко всему его наблюдению. Это позволяет
видеть отложенные поступления по старому размещению, но не даёт права суммировать
ROMI строк или считать его полностью созревшим результатом размещения.

CPA — на уникального покупателя с clean-долей этого размещения. CPL/CPF — на
наблюдаемую заявку/вступившего после касания. Несколько размещений могут касаться
одного человека; промежуточные счётчики разных строк не аддитивны.

`incrementality_evidence` принимает измерение эксперимента для размещения или
сценарную долю дополнительных поступлений для канала (`calibration`).
Во втором случае `k` находится в `[0,1]`, и
`ROMI_inc_est = (k × Revenue_clean − CashCost) / CashCost`.
Это допущение о дополнительных поступлениях, а не доказанный эффект и не
умножение готового ROMI на `k`. Значение не задаётся автоматически.
Импорт результата эксперимента (`experiment`) требует отдельного описания
источника; автоматически эксперимент система не проводит.

Аномалии: абсолютное отклонение дневной записанной выручки от среднего по полным
дням >2σ, минимум 7 полных дней, нет маркера размещения и действующего события в
календаре. Это диагностический сигнал, не статистический тест причины и не прогноз.

## Каналы и исчерпание

- Вступления/выходы/баны — переходы состояния, повтор статуса не добавляет переход.
  `status_check` уточняет состояние, но не создаёт фиктивное вступление.
- Исходящий источник группируется по первой наблюдаемой когорте. Это удержание
  приобретённой аудитории, а не доказательство исходного членства в рекламном канале.
- Число всех подписчиков берётся из `channel_snapshots`, а не из числа известных ID.
- NTS = уникальные впервые приобретённые этим размещением / его уникальные люди.
- CER = накопленные уникальные люди источника / последний известный размер аудитории.
- Частота канала = все касания источника / все уникальные люди источника. В таблице
  размещений дополнительно показана частота каждого отдельного размещения.
- Сигнал исчерпания: NTS < 20%, CER > 60%, последний размер аудитории не превышает
  снимок до прошлого размещения. Пороги — явная эвристика, не обученная модель.
  Недостающий снимок/знаменатель даёт «недостаточно данных».

## Когорты и завершённые события

Когорта определяется месяцем самого раннего наблюдения, точным диапазоном дат,
первым источником, типом и уверенностью. Поздний известный источник не подменяет
неизвестный первый источник. Unknown остаётся в реестре, но не приписывается
именованному источнику для clean/mixed денежных показателей.

Для каждого из 7/30/60/90 дней выбираются достигшие этого возраста участники.
Конверсия = доля этих людей с хотя бы одной положительной оплатой до границы.
Возврат уменьшает выручку, но не отменяет исторический факт первой покупки.
Без полного покрытия commerce конверсия/LTV не утверждаются; наблюдаемые покупки
и выручка остаются доступны. Состав созревшей группы между горизонтами может
различаться, поэтому кривая не гарантированно монотонна.

LTV — наблюдаемая нетто-выручка за горизонт / покупатели за тот же горизонт.
CAC — распределённая стоимость привлечения / покупатели полностью созревшей
90-дневной clean-когорты. Стоимость размещения распределяется между его первыми
пользователями, чтобы не назначать всю стоимость каждой месячной подгруппе.
Неограниченная пожизненная LTV не экстраполируется.

Для акции/гайда аудитория — наблюдаемые люди с касанием связанных размещений или
фактом отправки связанного предложения. Для мероприятия добавляются регистрации.
Один человек может входить в несколько активностей: их выручку нельзя складывать.

`Revenue_awakened` = поступления на 8–90-й день в **одной и той же** группе clean-
участников, созревших до 90 дней. Отдельно показывается часть с подтверждённой связью
заказа с последующей акцией. Отложенный ROMI доступен при зрелости всей аудитории
активности и нужном покрытии; иначе значение отсутствует.

Воронка мероприятия: зарегистрировался → сдал работу → организатор подтвердил
завершение → подтверждено членство в основном канале через 30 дней после окончания
→ купил после этого контрольного момента. Дополнительно показываются все покупатели
за 90 дней после регистрации, независимо от подписки.

Для удержания используется состояние к дате +30д при полном покрытии промежутка
от последнего подтверждения либо точная проверка в этот момент. Старое вступление
без подтверждённой непрерывности не доказывает сохранение подписки. При нескольких
основных каналах неоднозначная метрика не рассчитывается автоматически.

## Прогноз

Baseline «последнее значение» и seasonal-naive с периодом 7 не являются обученной
ML-моделью. Нужны минимум 35 полных дней сбора. Текущий неполный день исключается.
Проверка на прошлых датах использует значения и периоды, известные **на каждую**
дату среза. MAE/WAPE считаются по проверенным точкам выбранного горизонта.

80% прогнозный интервал — эмпирические квантили 10/90% прошлых ошибок отдельно
для каждого шага горизонта, минимум 20 ошибок на шаг. Это номинальный интервал;
его покрытие не гарантировано. Отрицательные пределы допустимы для нетто-выручки
с возвратами. При отсутствии факта или подтверждённого сбора факт не рисуется нулём.

`forecast_runs.origin_at` — дата информационного среза; `created_at` — когда
результат действительно сохранён. Ретропрогноз не маскируется под прогноз,
выпущенный в прошлом. `known_campaigns_json.known_at` сверяется с `recorded_at`
реальных размещений/версий акций; будущие записи отвергаются атомарно.

## Что не подключено извне

Реальные BotFather credentials и каналы; конкретная CRM/платёжный шлюз; автоматическое
получение аудитории внешних каналов (импортируются снимки); экспериментальные оценки
инкрементальности; ML-модель, обученная и проверенная на реальных данных.
Синтетические обученные модели подключены в отдельном ML-разделе. Для каждого есть данные/контракт или ясное
пустое состояние. Заменять их вымышленными бизнес-значениями система не пытается.
