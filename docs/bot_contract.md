# Контракт для ботов и системы продаж

Это спецификация API приёма данных. Реализация Telegram-коллектора теперь есть
в `collector.py`; её статус, проверенные команды и ограничения описаны в
[README ботов](../bots/README.md). Боевой Telegram и CRM пока не подключены.
Сначала создаются справочники
тем, каналов, курсов, пользователей; затем события, которые ссылаются на них.
Порядок таблиц в JSON не важен: загрузчик сам применяет зависимости.

## Общие правила

1. `user_id` — Telegram ID участника, полученный из проверенного взаимодействия.
   Не используйте username как постоянный ключ и не просите человека вручную
   вводить чужой числовой ID. У всех наших ботов один идентификатор пользователя.
2. Каждое событие получает стабильный ID. Например, префикс имени бота + update ID
   + тип события. Повторная доставка использует тот же ID. ID нельзя каждый раз
   генерировать заново, иначе повтор станет ещё одним действием.
3. Время события берётся из источника. `recorded_at` — когда факт стал известен
   аналитическому контуру. Если поле не передано, загрузчик ставит текущее UTC.
   При исторической загрузке нельзя подменять время регистрации временем события.
4. Все времена нормализуются в `YYYY-MM-DDTHH:MM:SS.ffffffZ`.
   В API допустим часовой пояс `+03:00`; на хранение попадёт UTC.
5. Для анкеты новое значение передаётся новым `profile_events.event_id`.
   Это ответ пользователя с источником, а не догадка по названию канала.
6. Для изменения цены или переноса курса создаётся `course_versions.version_id`.
   `effective_at` — с какого момента действует версия, `recorded_at` — когда о ней узнали.
7. Исторический импорт готовится в правильном хронологическом контексте:
   `users.first_seen_at` — начало доступного наблюдения, не дата регистрации Telegram.
   События раньше этого значения отклоняются. При первоначальной загрузке архива
   first_seen_at нужно определить по его ранним событиям до добавления пользователя.
8. Справочники и исходные события, уже сохранённые под одним ID, не перезаписываются.
   Адаптер `Store.user` может сдвинуть производное `users.first_seen_at` назад,
   если другой бот доставил более раннее событие; исходное событие и дата его
   регистрации остаются в журнале.
   Исправление ошибочных исходных фактов потребует отдельной миграции; API v1 не
   делает такую коррекцию молча.

## Что передают конкретные источники

| Источник | Таблицы / значения |
|---|---|
| Приход по рекламной ссылке | `acquisition_events`: user_id, placement_id, source_channel_id, mechanism, source_token |
| Бот-администратор нашего канала | `membership_events`: канал, участник, joined/left/banned, evidence_kind |
| Начальная проверка текущего членства | `membership_events` с `evidence_kind=status_check`; время проверки, а не выдуманная дата старого вступления |
| Меню бота | `activity_events`: topic_selected + topic_id |
| Кнопка программы/цены/листа ожидания | `course_program_requested` / `price_requested` / `waitlist_joined` + course_id |
| Запуск пробного занятия | `trial_started`; завершение задания — `trial_completed` |
| Мини-анкета | `profile_events` с education_stage или job_search_status |
| Хакатон | `participation_events`: registered, attended или solution_submitted |
| Система продаж | `orders` + `order_items` одним пакетом; затем события `payments` |
| Отправка предложения | `offers`: реальная предложенная цена, базовая цена, срок, sent/failed |
| Маркетолог в служебном боте | `placements`, фактические `placement_cost_events`, версии календаря курсов |

В `membership_events` передаётся ID участника, чей статус изменился, а не ID
администратора, выполнившего действие. Реализация коллектора должна различать
вступление, выход, блокировку и текущее подтверждённое состояние.
Членство фиксируем в собственных каналах, где предоставлены необходимые права.

Выбор темы и нажатие кнопки программы — наблюдаемые действия. Отправка сообщения
не является прочтением. Скачивание/прочтение PDF и просмотр поста не выдумываются.

Регистрация хакатона не считается участием. `attended` приходит из подтверждения
организатора, `solution_submitted` — из проверяемой сдачи работы. Повторное событие
того же мероприятия не увеличивает число разных посещённых хакатонов.

## Python-интерфейс

```python
from postupashki_data import connect, initialize, ingest

db = connect('data/postupashki.sqlite3')
initialize(db)  # Один раз при настройке, не на каждый входящий update.

# payload -- словарь, собранный адаптером из реальных событий.
# Не требуется заполнять таблицы, для которых в этом пакете нет новых строк.
result = ingest(db, payload)
db.close()
```

Один пакет может включать новый `users` и первое действие этого пользователя.
Если пользователь уже есть, адаптер не меняет его first_seen_at: передаёт только
новые события. Суммы в оплатах — копейки, тип int; строки и дроби отклоняются.

Состав пакета и все ограничения показаны в `schema_reference.md` и `schema.sql`.
Исполняемые примеры правильно сформированных строк есть в `tests/test_data.py`;
они специально вымышленные и не являются исходными данными бизнеса.

## Подтверждение покрытия

После успешно принятой и проверенной порции событий коллектор добавляет
`collection_periods`: уникальный period_id, domain, starts_at, ends_at, recorded_at.
Можно подтверждать часами или днями. Требуются шесть независимых доменов:

- `acquisition`: события наблюдаемого входа и источник;
- `membership`: изменения членства наших основных каналов;
- `activity`: все согласованные типы активности в наших ботах;
- `commerce`: заказы, состав, платежи и возвраты;
- `participation`: регистрации и подтверждённые участия;
- `offers`: успешные и неудачные отправки предложений.

Покрытие домена означает полноту согласованного контура, а не всех событий Telegram.
Если один из ботов этого домена был недоступен, нельзя подтверждать интервал как
полный. На запуске сборщика и после простоя начинайте новый интервал. Реальные
данные при отсутствии такого подтверждения сохраняются, но зависимые модельные
агрегаты могут быть NULL с причиной `incomplete_coverage`.

## Первые два ответа анкеты

`education_stage`: school, university, graduate, other, unknown.

`job_search_status`: not_searching, exploring, internship, job, interviewing, unknown.

Отсутствие ответа — отсутствие строки, не автоматически `unknown`. Категория
`unknown` может прийти явным ответом. Человек может одновременно быть university
и job: образование и поиск работы хранятся независимо.


## Расширение v2

Маркетолог передаёт карточки promotions, полные promotion_versions вместе с
promotion_courses, channel_snapshots, placement_metrics, tracking_links и
placement_promotions. Бот предложений — promotion_offers и promotion_responses;
система оформления заказа — order_promotions. Правила и список полей описаны
в marketing.md и schema_reference.md. Не записывайте ответ на неотправленное
предложение; повторные callback получают стабильные ID.

Новые домены collection_periods: ad_costs (расходы на рекламу), promotion_offers
(связи предложений с акциями), promotion_responses (реакции на предложения),
order_promotions (связи заказов с акциями). Они подтверждаются отдельно; старые
подтверждения offers и commerce не распространяются на эти новые потоки.

Для callback проверяйте, что Telegram ID нажавшего совпадает с users.user_id
получателя offers: ID предложения сам по себе не подтверждает личность нажавшего.


## Интегрированная сборка

Telegram-адаптер находится в `collector.py`, единственный слой записи — `store.py`.
Дополнения к схеме — `extension.sql`. При поздней доставке события адаптер может
сдвинуть вычисляемый `first_seen_at` назад к более раннему наблюдению; исходные
события не меняются. Прямой JSON-ingest по-прежнему не перезаписывает пользователя.
Подробные команды и новые сущности описаны в корневом README.
