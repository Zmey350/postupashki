# ML: прогнозы и сценарии поверх общей базы

**Статус: «Реализовано частично».** Обучение, подбор моделей, пакетный прогноз и вкладка общего дашборда работают на синтетической базе. Модели не обучались на реальных клиентах Поступашек; качество и экономический эффект для бизнеса не установлены. Для завершения нужны реальные журналы источников, решений, доставленных контактов и покупок с достаточной историей, затем повторное обучение и проверка на следующих периодах.

Общий запуск и согласованные бизнес-допущения — в [основном README](../README.md). ML не является ботом сбора: `postupashki_ml/` читает ту же SQLite-базу, а `ml_bridge.py` передаёт агрегаты в дашборд. Операционная аналитика и сбор работают без ML-зависимостей. Обучение запускается только командой; открытие веб-страницы его не запускает.

## Что реализовано

| Компонент | Статус | Проверка и оставшаяся работа |
|---|---|---|
| Признаки на историческую дату, временные разбиения, защита происхождения | Реализовано и проверено | Проверены поздние записи, будущие события, пробелы наблюдения, разбиения и несовместимые метки данных |
| Подбор трёх моделей и пакетный прогноз | Реализовано частично | 3 обучения по 8 кандидатов и команды прогнозирования выполнены; данные исключительно синтетические |
| ML-сценарии в общем дашборде | Реализовано частично | Общая база и API работают на демо; реальные модели отсутствуют |
| Доказательство причинного эффекта акции или рекламы | Только спроектировано | Журнал назначений и описательная сводка есть; бизнес-эксперименты не проводились |

## Воспроизведение

Команды выполняются **из корня проекта**, Python 3.12. Проверенный стек зафиксирован в `ml/requirements.txt`. Зависимости нужны только ML-командам. CatBoost, LightGBM и Streamlit для поставленной сборки не требуются; отдельного ML-дашборда нет.

```bash
python -m pip install -r ml/requirements.txt
python -m postupashki_ml --help
python -m unittest discover -s ml/tests -v
```

В поставке `data/demo.sqlite3` и `ml/models/` уже соответствуют друг другу. Для восстановления с нуля используйте новое имя базы — генератор намеренно отказывается перезаписывать существующую:

```bash
python build_demo.py --db data/reproduced.sqlite3 --seed 42 --users-per-wave 60
python -m postupashki_ml train --db data/reproduced.sqlite3 --out ml/reproduced_models --cutoff 2026-09-01 --max-trials 8 --jobs 2
```

Следующая команда обучения реально выполнена для поставляемой базы и создала все три артефакта заново; ранее сохранённые модели из отдельных проектов не использовались:

```bash
python -m postupashki_ml train --db data/demo.sqlite3 --out ml/models --cutoff 2026-09-01 --max-trials 8 --jobs 2
```

Дополнительные команды, выполненные при проверке:

```bash
python -m postupashki_ml init --db data/demo.sqlite3
python -m postupashki_ml customers --db data/demo.sqlite3 --as-of 2026-09-01 --plan ml/examples/promotion.json --economics ml/examples/economics.json --out ml/reports/customer_scenario.json
python -m postupashki_ml quote --db data/demo.sqlite3 --as-of 2026-09-01 --channel ch0 --incrementality 0.7 --economics ml/examples/economics.json --out ml/reports/channel_quote.json
python -m postupashki_ml portfolio --db data/demo.sqlite3 --as-of 2026-09-01 --channels ch0 ch1 ch2 --incrementality 0.7 --out ml/reports/channel_portfolio.json
python -m postupashki_ml compare --db data/demo.sqlite3 --as-of 2026-09-01 --plan ml/examples/scenarios.json --economics ml/examples/economics.json --out ml/reports/plan_comparison.json
```

`init` — только добавление ML-таблиц, без подмены бизнес-схемы. Команда `python -m postupashki_ml demo --db <новое-имя> --users-per-wave 60` создаёт только ML-симулятор; для общего продукта используйте `build_demo.py`. Числа и экономические параметры в `examples/` — **искусственные сценарии**, включая `incrementality=0.7`; это не оценка эффективности Поступашек. Все суммы с суффиксом `_minor` заданы в копейках.

## Задачи и смысл результатов

1. **Покупка курса в следующие 14 дней.** Вероятности считаются по каждому подходящему пользователю и суммируются в ожидаемое число покупателей. Доступны текущие условия и сценарий скидки/контактов. Пользователи, уже оплатившие курс и не получившие полный возврат, исключаются.
2. **Повторное размещение в известном канале.** Отдельные регрессии прогнозируют новых наблюдаемых людей за 7 дней и новых покупателей в течение 14 дней после прихода. Для расчёта нужен хотя бы один завершённый наблюдаемый выпуск рекламы.
3. **Предельный рекламный бюджет.** Прогноз количества покупателей переводится в условный потолок цены через маржу, требуемую доходность и явно заданную долю дополнительных покупок. Это не прогноз прайса канала и не доказанный оптимум.

Число новых покупателей ограничивается прогнозом новых людей. При неизвестной себестоимости результат экономики — `null`; отсутствие данных не заменяется нулём. Без `incrementality` поле `maximum_price_minor` также остаётся `null`. Отдельное `attributed_price_ceiling_minor` предполагает, что все атрибутированные покупки дополнительные. В интерфейсе это допущение нельзя скрывать.

## Как проводится обучение

Основной код обучения: `postupashki_ml/cli.py::train`; перебор и оценка — `postupashki_ml/search.py::run_search`. Признаки вычисляются в `customers.py` и `channels.py`, используя единственный общий пакет `postupashki_data`.

| Семейство | Вероятность покупки | Количества |
|---|---|---|
| Наивный ориентир | DummyClassifier | DummyRegressor |
| Линейная модель | LogisticRegression | PoissonRegressor |
| Бустинг | HistGradientBoostingClassifier | HistGradientBoostingRegressor с Poisson-loss |
| Случайные деревья | ExtraTreesClassifier | ExtraTreesRegressor |

Если CatBoost или LightGBM установлены пользователем, поиск обнаруживает их и добавляет кандидатов; в проверенном окружении они отсутствовали. `--full` расширяет сетку гиперпараметров и преобразований, `--max-trials` ограничивает бюджет. Полный поиск не заявляется как выполненный.

Линейная модель даёт компактный ориентир для вероятностей/счётчиков; деревья проверяют нелинейность и взаимодействия. Поэтому выбор делается по следующему периоду, а не по сложности модели. Всем кандидатам подаются одни и те же доступные на дату события. Операции заполнения пропусков, масштабирования и кодирования категорий обучаются внутри каждого тренировочного окна.

Признаки контактов используют экспоненциальное или Weibull-затухание и насыщение: недавний контакт может значить больше давнего, очередной контакт — меньше первого. Параметры тоже участвуют в подборе. Это моделирующее предположение, а не обнаруженный закон поведения. Признаки давления позволяют модели выучить и отрицательную связь частых контактов с покупкой.

Два последовательных временных окна подбора, затем отдельные периоды калибровки и итогового теста. Обучающие метки должны завершиться до начала следующего периода; перекрывающиеся окна исключаются. Калибратор вероятностей обучается только на своём периоде. Для счётчиков выдаётся эмпирический диапазон ошибки по калибровочному периоду, без гарантии покрытия при изменении аудитории.

## Что проверено на синтетике

Набор seed 42: **6 616 пользователей, 96 размещений, 1 260 заказов, 1 593 платёжных события, 1 080 решений, 4 117 контактов**. Решения содержат 212 положительных меток покупки; это не число всех покупок в базе. 61 клиентский признак и 36 признаков канала.

| Задача | Выбранная модель | Обучение / калибровка / тест | Метрика на тесте | Наивный ориентир |
|---|---|---:|---:|---:|
| Покупка | LogisticRegression | 780 / 120 / 180 | LogLoss 0,4683 | 0,5004 |
| Новые люди | ExtraTreesRegressor | 64 / 10 / 13 | MAE 11,20 | 24,03 |
| Новые покупатели | ExtraTreesRegressor | 64 / 10 / 13 | MAE 4,66 | 7,12 |

Из 96 размещений 9 исключены из финального обучения/калибровки/теста из-за временных границ; они остаются в исходной истории. Каждая задача проверила 8 кандидатов. Эти результаты показывают исправность воспроизводимого процесса на симуляторе, **не точность на бизнес-данных**. Тест рекламы содержит всего 13 размещений.

23 ML-теста прошли без пропусков: [протокол](reports/tests.txt). Проверены частичные платежи, возвраты, временные утечки, полнота наблюдения, дедупликация прихода, независимость прогнозов от размера батча, нулевой сценарий, ограничения экономики, происхождение данных и общий API. Тесты интеграции требуют демо и обученных моделей; если файлов нет, они явно пропускаются.

Точные метрики, параметры, границы дат и все ошибки отдельных кандидатов находятся в `models/*_report.json`, итог — `models/training_summary.json`. Синтетические прогнозы тестовых строк — `models/*_test_predictions.csv`. `joblib`-файлы следует загружать только из доверенной сборки или собственного обучения; чтение этих файлов исполняет Python-сериализацию. Модель проверяет совместимость версии scikit-learn, дату доступности и происхождение базы.

## Три уровня знания и реальные данные

**Что мы знаем:** только реально записанные события и их время получения, платежи, версия предложения, подтверждённый приход по размеченному источнику. В демо эти события искусственные. Доставленное сообщение не доказывает прочтение, доступность поста не доказывает индивидуальный просмотр.

**Что мы оцениваем:** вероятность покупки, будущий приток, условное сравнение планов, распределённую по первому наблюдаемому источнику выручку, потолок цены при выбранных допущениях. Сценарная разница прогнозов не является причинным эффектом.

**Что пока узнать нельзя:** сколько дополнительных покупок вызвала реклама/скидка, кто прочитал пост в чужом канале, полное пересечение аудиторий и эффект на новых для нас аудиториях. Нужны контрольные группы с реальными случайными назначениями, непрерывные журналы сбора, согласованная связь с оплатой и разрешённые платформой события.

Для обучения на своей базе сначала организуйте запись исходных событий через общий импорт/ботов, подтвердите происхождение `real`, затем добавьте ML-таблицы командой `init`. `ml_decisions` хранит план **до** наступления исхода (включая контроль без действий); `ml_contacts` хранит факт доставки/участия отдельно; `ml_contact_periods` фиксирует законченные интервалы наблюдения. Эти журналы не заполняются автоматически на основании будущих покупок. Если решений нет, код строит наблюдательные окна без заранее назначенных воздействий: такой режим не восстанавливает эксперимент.

Покупка в ML-метке означает первое полное погашение положительного заказа в заданном окне для выбранного курса; поздний возврат не стирает исторический факт оплаты. Для владения курсом учитывается остаток платежей. Возвраты/комиссии для будущей экономики задаются явно. Общие правила заказов, пакетов и операционной выручки описаны в основном README.
